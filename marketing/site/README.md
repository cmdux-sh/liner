# Liner Marketing Site

Astro site for the Liner landing page, docs, and changelog.

## Current State

- Main page: `src/pages/index.astro`
- Changelog: `src/pages/changelog.astro`
- Docs content: `src/content/docs/docs/`
- Product context: `PRODUCT.md`
- Design system: `DESIGN.md`
- Marketing copy guide: `MARKETING_COPY_BEST_PRACTICES.md`
- Global styling and animation tokens: `src/styles/global.css`
- Docs and changelog styling: `src/styles/starlight.css`
- Layout shell and metadata: `src/layouts/BaseLayout.astro`
- Brand logo asset: `public/liner-logo.svg`
- Install CTA command: `npx linersh`
- Product version shown in the page: `1.1.1`, matching `packages/tui/package.json`

The current landing page is a single long-form brand page with a terminal-native visual language: dark workspace, orange install panel, WebGL product shot, method rail, live terminal demo, install CTA, practical-edge cards, and footer marquee. The public product story starts with the plain object: a local CLI and terminal UI that turns focused research sources into files an AI assistant can use later. Internal nouns such as project, corpus, Operating Layer, Corpus Ready, and Project Complete should appear only after the page has explained the local folder, saved sources, compiled research, and AI instructions.

The docs use Starlight inside the same Astro app. They are styled to match the landing page rather than the default Starlight look: same header, compact mono navigation, orange active states, dark grid, shared command snippets, and shared file-tree components.

The changelog is a custom Astro page, not a Starlight content page. It uses the same shared header and command/file components, with a narrower readable measure for release notes.

Before editing public copy or layout, read `PRODUCT.md`, `DESIGN.md`, and `MARKETING_COPY_BEST_PRACTICES.md`.

## Deploying To Vercel

This site is deployed manually from `marketing/site`; it does not need Vercel's Git integration for the whole monorepo.

One-time setup:

```sh
cd marketing/site
vercel link --project liner-site
vercel env add PUBLIC_POSTHOG_KEY production
vercel env add PUBLIC_POSTHOG_HOST production
```

Use these env values:

```text
PUBLIC_POSTHOG_KEY=<PostHog Project API key, starts with phc_>
PUBLIC_POSTHOG_HOST=https://us.i.posthog.com
```

Preview deploy:

```sh
cd marketing/site
vercel deploy \
  -b PUBLIC_POSTHOG_KEY=<PostHog Project API key, starts with phc_> \
  -b PUBLIC_POSTHOG_HOST=https://us.i.posthog.com
```

Production deploy:

```sh
cd marketing/site
vercel deploy --prod
```

Canonical domain is `www.liner.sh`; `liner.sh` redirects to it via `vercel.json`.

After the project is linked, add both domains to the same Vercel project:

```sh
vercel domains add www.liner.sh liner-site
vercel domains add liner.sh liner-site
```

## Design Notes

- The page uses Astro plus Tailwind CSS classes.
- Icons in new UI controls should use `src/components/Icon.astro`.
- Docs are powered by Starlight. The Starlight header is overridden by `src/components/starlight/Header.astro` so it renders the shared `SiteHeader.astro`.
- Use `CommandSnippet.astro` for copyable shell commands and command output.
- Use `FileTree.astro` for folder trees and generated output examples.
- Keep docs headings, command snippets, and page navigation compact. The site should feel like a tool manual, not an editorial page.
- Search is generated by Starlight/Pagefind during production build. A production-only warning in dev is expected.
- `public/sitemap.xml` is intentionally absent. `@astrojs/sitemap` generates sitemap output during build.
- The hero WebGL canvas depends on its parent size and has a `ResizeObserver`.
- The marquee tracks are hydrated by an inline script so wide screens do not show an empty gap.
- Copy buttons all share `.copy-install-cmd` and copy `npx linersh`.
- The terminal mock has its scrollbar hidden intentionally.
- PostHog is disabled on `localhost`, `127.0.0.1`, `::1`, and `.local` hosts.
- PostHog tracks pageviews plus explicit high-intent events: install command copies, GitHub clicks, changelog clicks, project links, and outbound links.

## Copy Rules

Read `MARKETING_COPY_BEST_PRACTICES.md` before changing public marketing copy.

Rendered marketing copy should avoid:

- em dashes
- "not this, but this" contrast framing
- stale "framework" language for Liner
- literal question-answer headings such as "How is this different?"
- internal milestone labels before they have been explained

Preferred language:

- Liner is a local CLI and terminal UI for turning focused research sources into files your AI assistant can use later.
- The user gives it URLs, transcripts, PDFs, local files, or pasted text.
- The tool saves sources and notes, compiles the research into `MIXTAPE.md`, and writes instructions in `LINER.md` and `SKILL.md`.
- A quick AI answer is enough when the user only needs a response. The saved-folder path is for source choices, evidence trails, and task instructions that need to survive later work.

Truth rules:

- Do not imply a public project gallery or library exists yet.
- Use example jobs as examples, not as shipped project inventory.
- Keep browser capture, public library, advanced audits, composition, and external-use evidence out of public marketing copy unless clearly marked as future work.
- Avoid repeating "Liner" in adjacent paragraphs when "the project", "the folder", "the TUI", or "the workflow" is clearer.

## Verification

Before handing off changes:

```sh
npm run build
rg -n "—|–|\\b[Bb]ut\\b|\\b[Nn]ot\\b|isn't|aren't|doesn't|don't|can't|couldn't|without|instead|rather than|Without" src/pages/index.astro src/layouts/BaseLayout.astro
```

The `rg` command exits with code `1` when it finds nothing, which is the expected clean result.

For docs and changelog edits, also spot-check:

- `/docs/`
- `/docs/install/`
- `/docs/tape-format/`
- `/docs/troubleshooting/`
- `/changelog/`

Watch for command snippets getting too large, mobile command wrapping, low-contrast syntax colors, docs containers drifting wider than the landing-page grid, and stale claims about the TUI or CLI.
